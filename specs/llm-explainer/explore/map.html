1 · Known knowns settled ground, with sources

The reference: airsup.ai/rocket-engine

Sources: the tweet's video frames, the page's HTML and help text, and its JS bundle (fetched 2026-09-27).

  • A lab of machines, with a switcher at the bottom and a house button for the overview. Every machine uses the same template:
    • top left: a title (“Inside the Raptor 3”), a 2-line pitch, 3 stat chips (280 tf · 350 bar · 800 kg/s) and a caption that changes with Follow;
    • top right: a Follow row (All plus 3 things to follow, also on keys 1–4), one slider, a scenario row, Whole / Cutaway / Exploded, play and help;
    • labels pinned to parts in the 3D view.
  • The help panel states where each machine's numbers come from (“Thrust and Isp follow SpaceX's published figures… everything else is an estimate”). That honesty is part of the style.
  • Built with React, three.js on WebGL and OrbitControls, with procedural geometry, a dark room and bloom. For us, only the look and feel carries over; the tech doesn't (see D10).

The territory

  • Monorepo scaffold: package.json (bun workspaces apps/*, packages/*, catalog), turbo.json, packages/typescript-config/base.json, .oxfmtrc.json. Modelled on ~/dev/jevgrep.
  • Skills are in .agents/skills/, symlinked from .claude/skills/. The renderer skill (.agents/skills/renderer/SKILL.md) prescribes TypeGPU on WebGPU, no second rendering library, one frame function, one resource registry, pmndrs math, numbers kept in data, and an injectable clock.
  • Blender 5.2.1 LTS is at /Applications/Blender.app. ~/dev/3d-harness/sandbox has a Docker image with scripted Blender and MCP. Its README records the axis conversion: Blender (x,y,z) → glTF (x,z,-y).
  • ~/dev/3d-harness/apps/workbench/scripts/verify.mjs captures with Playwright launch({ headless: true, channel: 'chrome' }), i.e. real Chrome with WebGPU.
  • Prior art to avoid imitating: bbycroft.net/llm. It's jargon-heavy and shows the whole tower of matrices, which the user found confusing.

4 · Unknown unknowns landmines, worst first

The sweep covered the scaffold (package.json, turbo.json, .oxfmtrc.json, packages/typescript-config), the renderer skill, 3d-harness's capture setup, and the npm/Python toolchain. It's a greenfield repo, so there were no prior attempts to learn from.

1 · 16 chapters in 10 minutes D24

Evidence
D21 and D22 together give about 37 seconds per chapter. D12 is free exploration, and D17's storyteller captions run long.
Why it bites
A first-time visitor on free exploration won't find a chapter's point in 37 seconds.
Decision
D24: each chapter plays its main moment on arrival, as a 20–30 second loop with no clicks. The caption is 2 storyteller sentences, with “Precisely:” behind one click. The controls stay available for exploring, and → steps through the ladder.

2 · Tiny models may not show a chapter's effect D25

Evidence
A tiny model trained on children's stories may not reliably link “it” → “cat”, and the no-positions model may not visibly fail on “dog bites man”.
Why it bites
It's tempting to fake the picture, and that breaks D9's honesty.
Decision
D25: nothing on screen is faked. Example prompts are chosen by running the models (O2). If an effect doesn't show, train that model bigger or longer. If it still doesn't show, the chapter says so. Stat chips always name their scale: “this tiny model” or “Llama-3-8B”.

3 · The browser can't show GPU memory speed D27

Evidence
Chapters 11–15 (KV cache, batching, quantization, speculative decoding, MoE) are about memory-bandwidth-bound decode on a GPU. A tiny model running on the CPU isn't limited by memory.
Why it bites
Browser timings would teach the wrong lesson.
Decision
D27: what happens to tokens is real (which drafts get accepted, which expert is chosen, quantized output). Speed and throughput come from Llama-3-8B arithmetic on a named GPU (O4). Browser timing is never shown as “speed”.

4 · One tokenizer for every model D28

Evidence
Speculative decoding compares the drafting and checking models token for token.
Decision
D28: chapter 1 trains the tokenizer once, and every later model uses it. Chapter 0 counts whole words, before tokenization has been introduced.

5 · The chapter 4 model is a bad drafter D26

Evidence
It has no positions and no MLP, so its guesses would rarely be accepted.
Why it bites
The chapter would teach that speculative decoding doesn't work.
Decision
D26 (amends D9): the drafter is the smallest full-architecture model (1 layer). The best measured acceptance rate wins (O3).

6 · The MoE router collapses sharp edge

Why it bites
A tiny router with no load-balancing term sends everything to one or two experts, so 6 of the 8 on screen sit idle.
Rule
Train the chapter 15 model with a load-balancing auxiliary loss, and check that expert usage is spread out before exporting.

7 · X is mostly phones; phones get the fallback D29

Evidence
D19 (post on X) + D20 (desktop only) + D10 (WebGPU only).
Why it bites
The message page is the first impression for most people who see the post.
Decision
D29: the fallback plays a recorded video of the real app (captured with the deterministic clock), with a “copy link to open on desktop” button. The same page is shown when WebGPU is missing. Each chapter gets a deep link (/#4) and a link-preview image.

8 · Screenshot checks need the real GPU sharp edge

Evidence
The mock check used headless Chrome with --disable-gpu, which has no WebGPU. 3d-harness verify.mjs uses Playwright channel: 'chrome'.
Rule
Copy the 3d-harness launch setup. Treat any WebGPU validation warning or console error as a failed render (renderer skill).

9 · Labels and bloom are ours to build sharp edge

Evidence
D10 means no three.js. HTML labels projected with the shared camera float through solid geometry.
Rule
Hide labels with a CPU occlusion test against the app's own shapes, using the camera function the GPU packing uses. Bloom needs an rgba16float HDR target and a blur chain in the one frame function. The orbit / zoom / pan controls are also built by hand. All of this is in slice 1.

10 · Toolchain gaps D30

Evidence
python3 -c "import torch" fails because torch isn't installed. uv 0.12.10 is installed. npm: typegpu@0.12.6 and math@0.1.0 (pmndrs) are both young.
Decision
D30: training/ is a uv project with pinned torch on MPS. Exported weights are committed (a few MB), so Vercel never trains. Pin exact versions of typegpu and math, and expect API churn.

Confirm before coding small facts, not footnotes

  • Llama-3-8B config values from the published config.json: 32 layers, 32 query heads, 8 KV heads, hidden 4096, head_dim 128, FFN 14336, vocab 128256. The walk quoted 128 KiB of KV cache per token (2 × 32 × 8 × 128 × 2 bytes). Recompute it from the real file.
  • Read the typegpu@0.12.6 docs and math@0.1.0 API.md before designing the registry and camera.
  • Confirm that Playwright + real Chrome headless gets hardware WebGPU on this Mac (Apple GPU).
  • Check which way the Blender 5.2 glTF exporter converts axes against 3d-harness's note, with one test prop.
  • Confirm the H100 (or chosen GPU) bandwidth and FLOPs from the spec sheet (O4).
  • Check the TinyStories licence (O1).

Judgment calls: tweak these
  • On-screen numbering: renumber to a contiguous 0–15 now that training is cut. Alternative: keep the gap for a later training chapter.
  • Tiny model sizes (invented starting values; tune by D25): hidden width 64–256, 1–4 layers, 4 heads, 128-token context, a shared BPE vocab of about 2–4k. Alternative: character-level for chapters 0–3 only.
